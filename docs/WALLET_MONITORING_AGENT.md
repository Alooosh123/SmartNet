# تصميم Wallet Monitoring Agent في SmartNet

> الحالة: مواصفة تصميم معتمدة للتنفيذ على الفرع `production-hardening`.
> هذه الوثيقة لا تعني أن تطبيق Android أو استقبال المحافظ أو التفعيل الآلي قد نُفّذ أو اختُبر مع محفظة حقيقية.

## 1. القرار المعماري

يعتمد SmartNet على **هاتف Android مخصص** بوصفه جامع إشعارات المحافظ. يلتقط تطبيق مرافق إشعارات تطبيقات المحافظ المحددة فقط، ويحوّلها إلى أحداث موحدة ثم يرسلها إلى Backend عبر HTTPS.

الهاتف ليس بوابة دفع ولا مصدر حقيقة مالية مستقلاً. الإشعار إشارة واردة تحتاج إلى تحليل ومطابقة وتحقق حتمي قبل أن تتحول إلى معاملة مسوّاة أو تفعيل اشتراك.

### مبادئ لا يمكن تجاوزها

- لا تُخزّن أرقام PIN أو كلمات مرور المحافظ أو OTP أو بيانات تسجيل الدخول داخل SmartNet أو تطبيق الهاتف.
- لا نستخدم Accessibility Service أو التقاط الشاشة أو OCR أو قراءة SMS كبديل لواجهات الإشعارات.
- يعمل الجامع وفق قائمة سماح package allowlist لأسماء الحزم الرسمية التي جرى اختبارها لكل محفظة. لا يجمع إشعارات بقية الهاتف.
- لا يستطيع تطبيق الهاتف تفعيل اشتراك أو تعديل بيانات عميل أو تنفيذ أمر MikroTik. وظيفته إرسال حدث فقط.
- لا يكفي نص إشعار مبهم أو صورة حوالة أو اسم مرسل متشابه لاعتماد الدفع.
- لا يجوز للذكاء الاصطناعي اتخاذ قرار مالي. يمكنه اقتراح استخراج حقول من نص غير معروف، لكن محرك قواعد ثابت هو صاحب قرار المطابقة والاعتماد.
- جميع المبالغ تستخدم Decimal/Numeric والعملة تطابق عملة طلب الدفع حرفياً؛ لا يوجد تحويل عملة ضمني.

## 2. المكونات

### A. Android Wallet Collector

تطبيق Android أصلي صغير (Kotlin) مستقل عن لوحة React الحالية، يعمل على هاتف مخصص موصول بالطاقة والإنترنت قدر الإمكان.

المسؤوليات:
1. تسجيل الهاتف لدى SmartNet عبر رمز اقتران لمرة واحدة، قصير الصلاحية.
2. التأكد من منح Notification Access وعرض حالة الاتصال والصلاحية بوضوح.
3. استقبال أحداث `NotificationListenerService` بعد اتصال الخدمة بالنظام.
4. قبول إشعارات حزم المحافظ المسموح بها فقط، مع استبعاد OTP والرسائل العامة والإشعارات غير المالية.
5. استخراج النصوص المتاحة فقط، واسم الحزمة ووقت الإشعار ومعرف محلي عشوائي للحدث.
6. إرسال الحدث إلى SmartNet عبر HTTPS، مع توقيع طلب ووقت وnonce ومعرف فريد.
7. تخزين طابور مؤقت مشفر محلياً عند انقطاع الشبكة، ثم إعادة الإرسال حتى استلام ACK من الخادم.
8. إرسال heartbeat يوضح أن الهاتف متصل وأن صلاحية الإشعارات ما زالت ممنوحة.

لا يعد الجامع الإشعار دليلاً على التسوية، ولا يحاول إعادة فتح تطبيق المحفظة أو النقر داخله أو قراءة بيانات مخفية.

### B. Wallet Event Intake API

بوابة استقبال في FastAPI تتحقق من:
- أن الجهاز مسجل ونشط ولم يتم إلغاؤه.
- صحة توقيع الجهاز، والطابع الزمني ضمن نافذة قصيرة، وعدم إعادة استخدام nonce.
- أن الحزمة مسموح بها وأن حجم الحدث ضمن الحد.
- أن معرف الحدث لم يصل سابقاً.

تخزن الحدث وتعيد ACK idempotent. لا تنفذ التفعيل ضمن HTTP request؛ المعالجة تتم عبر عامل خلفي قابل لإعادة المحاولة.

### C. Provider Notification Adapters

كل محفظة لها Adapter مستقل يعرّف:
- package names الموثقة لتطبيق المحفظة.
- إصدارات التطبيق/قوالب الإشعار التي اختُبرت.
- قواعد قراءة اللغة العربية والإنجليزية والأرقام العربية/الهندية وعلامات العملة.
- حقول المرسل والمستقبل والمبلغ والعملة والمرجع ومعرف العملية والوقت.
- قاموس حالات المحفظة وتحويلها إلى `settled`, `pending`, `failed`, `reversed`, أو `unknown`.

لا يوجد Parser عام يفترض أن عبارة واحدة تعني النجاح في كل المحافظ. أي تغيير في تنسيق الإشعار أو تطبيق المحفظة يجعل الحدث `unknown_format` حتى يحدّث Adapter ويجتاز اختباراته.

### D. Deterministic Matching & Risk Engine

يقوم بالتحقق من هوية مصدر الإشعار والحقول المالية، ثم يبحث عن طلب دفع واحد فقط تنطبق عليه جميع الشروط. الحالات غير المكتملة أو المتعارضة تذهب إلى مراجعة مالية.

### E. Subscription Fulfilment Worker

ينفذ التفعيل أو التجديد بعد تثبيت المعاملة والطلب في قاعدة البيانات، باستخدام معاملة DB واحدة وقفل للسجل ومفتاح idempotency. لا ينفذ أي تغييرات RouterOS مباشرة.

### F. لوحة الإدارة

تضيف صفحات:
- حالة الهاتف: متصل/منقطع، آخر heartbeat، صلاحية الإشعارات، إصدار التطبيق، آخر حدث.
- حسابات الاستقبال: المحفظة، رقم/معرّف حساب الاستقبال، العملة، الحالة، والهاتف الذي يستقبل إشعاراته.
- هويات محافظ أصحاب الشبكات: رقم المرسل، صاحب الشبكة، المحفظة، حالة التحقق، سجل الموافقات.
- الأحداث الواردة: مكتشف، غير قابل للتحليل، مكرر، قيد المطابقة، أو يحتاج مراجعة.
- المعاملات: المبلغ والعملة والمرسل والمستقبل والمرجع ونتيجة المطابقة.
- قائمة المراجعة: اختلاف المبلغ، مجهول المرسل، أكثر من طلب مطابق، حالة غير نهائية، أو مرجع مكرر.
- إيقاف الجهاز أو محفظة الاستقبال أو رقم المرسل فوراً.

## 3. التسجيل الأولي وربط رقم صاحب الشبكة

يجب فصل هويتين مختلفتين:

1. **محفظة صاحب الشبكة (Payer Wallet Identity):** الرقم الذي يرسل منه صاحب الشبكة المبلغ.
2. **محفظة استقبال المنصة (Receiving Wallet):** حساب التاجر الذي يستقبل التحويلات وتصل إشعاراته إلى الهاتف المخصص.

خطوات اعتماد رقم المرسل لأول مرة:
1. صاحب الشبكة يسجل حسابه ويضيف نوع المحفظة ورقم المرسل واسم صاحب الرقم والبيانات المطلوبة.
2. يُنشأ سجل بحالة `pending_approval`، ولا يحصل الرقم على صلاحية الدفع التلقائي بعد.
3. يحدد النظام طلب اشتراك/تجديد أولياً، ويعرض بيانات محفظة الاستقبال والمبلغ والعملة.
4. تصل حوالة الاختبار/أول دفعة إلى هاتف الاستقبال.
5. يرى مسؤول المالية الحدث في لوحة SmartNet، ويتحقق من الحوالة داخل تطبيق المحفظة نفسه ومن ملكية الرقم حسب إجراءات العمل المعتمدة.
6. يوافق مسؤول مخوّل على ربط (المحفظة + رقم المرسل + حساب صاحب الشبكة)، ويُسجل من وافق ومتى وعلى أي دليل.
7. يمكن بعد ذلك تفعيل الدفع الآلي لهذا الربط، بشرط أن يظل نشطاً وأن تنجح كل قواعد التحقق أدناه.

رقم المرسل لا يصبح موثوقاً لمجرد ظهوره في إشعار واحد. يمكن لصاحب الشبكة إضافة أكثر من محفظة بعد موافقة مستقلة لكل واحدة. مشاركة الرقم بين أكثر من صاحب شبكة ممنوعة افتراضياً، ولا تسمح إلا باستثناء موثق يوافق عليه المدير.

## 4. نموذج البيانات المقترح

تضاف الجداول التالية عبر Alembic migrations، مع إبقاء الجداول الحالية متوافقة أثناء الانتقال:

| الجدول | الغرض والحقول الأساسية |
|---|---|
| `wallet_monitor_devices` | `id`, `device_uuid`, `name`, `status`, `credential_hash`, `last_seen_at`, `app_version`, `notification_access_granted`, `revoked_at` |
| `wallet_providers` | `id`, `code`, `display_name`, `enabled`, `parser_version`, `allowed_packages` |
| `receiving_wallet_accounts` | `id`, `provider_id`, `device_id`, `account_label`, `account_identifier_encrypted`, `account_fingerprint`, `currency`, `status` |
| `payer_wallet_identities` | `id`, `client_id`, `provider_id`, `phone_encrypted`, `phone_fingerprint`, `owner_name`, `status`, `approved_by`, `approved_at`, `revoked_at` |
| `wallet_notification_events` | `id`, `device_id`, `event_uuid`, `package_name`, `notification_posted_at`, `received_at`, `payload_hash`, `encrypted_payload`, `parse_status`, `parser_version`; قيد فريد على `(device_id,event_uuid)` |
| `payment_intents` | `id`, `client_id` أو `registration_id`, `intent_type` (initial/renewal), `plan`, `amount NUMERIC`, `currency`, `receiving_wallet_id`, `payer_wallet_identity_id`, `reference_token`, `expires_at`, `status` |

### حماية أرقام المحافظ والنصوص

- تخزن أرقام المحافظ ومعرفات الحسابات الحساسة مشفرة بمفتاح خارج قاعدة البيانات.
- ينشأ HMAC fingerprint للبحث ومنع التكرار دون الحاجة إلى تخزين الرقم مكشوفاً في الفهارس والسجلات.
- يمنع تسجيل نص الإشعار الكامل أو الأرقام في logs. يخزن النص الخام مشفراً، وتحدد له مدة احتفاظ قصيرة قابلة للضبط، ثم يحذف مع الإبقاء على hash والحقول المحاسبية اللازمة.
- لا تحفظ بيانات اعتماد المحفظة أو OTP في أي جدول.
- تطبق قيود فريدة على معرفات الجهاز والأحداث ومعرفات معاملات المزود ومراجع التحويل، مع معالجة تعارضات السباق داخل DB.

## 5. عقد API المقترح

| المسار | الغرض | الصلاحية |
|---|---|---|
| `POST /api/v1/wallet-monitor/enroll` | اقتران الهاتف برمز لمرة واحدة | رمز اقتران محدود |
| `POST /api/v1/wallet-monitor/heartbeat` | تحديث الاتصال وصلاحية Notification Access | جهاز مسجل |
| `POST /api/v1/wallet-monitor/events` | إرسال حدث إشعار موحد | جهاز مسجل + توقيع |
| `GET /api/v1/admin/wallet-monitor/devices` | متابعة الأجهزة | مدير |
| `POST /api/v1/admin/wallet-monitor/devices/{id}/revoke` | إلغاء جهاز | مدير |
| `POST /api/v1/clients/me/payer-wallets` | طلب ربط رقم محفظة مرسل | صاحب الحساب |
| `POST /api/v1/admin/payer-wallets/{id}/approve` | اعتماد الربط الأولي | مالية مخولة |
| `POST /api/v1/clients/me/payment-intents` | إنشاء طلب اشتراك/تجديد | صاحب الحساب |
| `GET /api/v1/admin/wallet-monitor/reviews` | قائمة الحالات غير المحسومة | مالية مخولة |
| `POST /api/v1/admin/wallet-monitor/reviews/{id}/decision` | اعتماد/رفض بعد التحقق اليدوي | مالية مخولة |

الـAPI الخاص بالجهاز لا يقبل `client_id` أو قرار تفعيل من الهاتف. العميل لا يختار بنفسه حالة `settled`؛ هذه الحالة يحددها Adapter بعد تفسير قالب معروف، ثم يتحقق المحرك من بقية الشروط.

## 6. قواعد التحقق الآلي

لا يسمح بالتفعيل الآلي إلا إذا تحققت **كل** الشروط التالية:

1. الحدث صادر من جهاز مسجل وغير ملغى، وتوقيعه وnonce والطابع الزمني صالحون.
2. اسم الحزمة ضمن قائمة سماح المزود، وقالب الإشعار معروف ومختبر وإصدار Parser معتمد.
3. الإشعار يصف تحويلاً وارداً إلى حساب استقبال المنصة الصحيح، لا تحويلاً صادراً أو إشعاراً إعلانياً.
4. حالة العملية mapped صراحة إلى `settled` أو نجاح نهائي لدى ذلك المزود. لا تُستنتج التسوية من كلمات عامة مثل «تم» دون اختبار دلالتها الخاصة بالمحفظة.
5. رقم المرسل يطابق تماماً هوية محفظة معتمدة ونشطة ومربوطة بصاحب الشبكة المطلوب.
6. حساب الاستقبال يطابق حساب الدفع المحدد في طلب الدفع.
7. المبلغ يساوي قيمة الطلب بدقة Decimal، والعملة متطابقة تماماً.
8. يوجد مرجع أو معرف معاملة ثابت وفريد من المزود. إذا لم توفر المحفظة معرفاً ثابتاً، لا يُفعّل الدفع تلقائياً إلى أن توجد آلية بديلة موثوقة ومختبرة تمنع تكرار المعاملة.
9. يوجد Payment Intent واحد فقط مفتوح يطابق صاحب الحساب والمحفظة المستقبلة والمبلغ والعملة والوقت والمرجع.
10. لم تنقض صلاحية الطلب، ولم تستخدم العملية سابقاً، ولا توجد إشارة عكس/استرداد/إلغاء.
11. لم يكن الحساب موقوفاً إدارياً، ولم تتجاوز المعاملة قواعد المخاطر.

### حالات التحويل إلى المراجعة اليدوية

- المرسل غير معروف أو الربط غير معتمد/ملغى.
- اسم الحزمة أو قالب الإشعار غير معروف، أو تغيّر إصدار تطبيق المحفظة.
- غياب مبلغ أو عملة أو مستقبل أو مرجع/معرف فريد.
- مبلغ جزئي أو زائد، أو عملة مختلفة.
- أكثر من طلب واحد يمكن أن يطابق الإشعار.
- إشعار مكرر أو عملية قديمة أو حالة pending/failed/unknown.
- بيانات متناقضة بين نصوص الإشعار.
- وصول الحدث بعد فترة انقطاع طويلة أو من جهاز فقد سلامة الثقة.

**لا تُجمع دفعتان جزئيتان آلياً، ولا يقسّم مبلغ زائد على عدة طلبات، ولا يمنح رصيد تلقائي من إشعار غير محسوم.** يمكن إضافة هذه السياسات لاحقاً بموافقات محاسبية مستقلة.

## 7. التفعيل والتجديد

### الاشتراك الأول

- ينشأ Payment Intent مرتبط بـ Registration Request وباقة محددة ومدة وسعر وعملة وحساب استقبال.
- عند تحقق الدفع، ينشأ Fulfillment فريد؛ وفي DB transaction واحدة يتم إنشاء Client أو ربطه بطلب التسجيل وتسجيل تاريخ الانتهاء والصلاحيات وسجل التدقيق.
- لا يفتح الاشتراك قبل تثبيت المعاملة والـFulfillment.

### تجديد اشتراك قائم

- ينشئ العميل طلب تجديد مرتبطاً بحسابه وباقة/مدة واضحة، ولا يعدّل ذلك صلاحياته بمجرد إنشاء الطلب.
- بعد تحقق التحويل، يقفل النظام سجلي Payment Intent وClient لتجنب التجديد المتزامن مرتين.
- يحسب الانتهاء الجديد بهذه القاعدة:

`new_expiry = max(current_expiry, now_utc) + plan_duration`

- يسجل `previous_expiry`, `new_expiry`, `transaction_id`, `intent_id`, الباقة والمدة في Fulfillment فريد.
- إذا أعيد إرسال الإشعار أو أعاد العامل المحاولة، لا تتغير مدة الاشتراك مرة ثانية.
- إذا كان الحساب موقوفاً إدارياً، يمكن تسجيل الدفع كمدفوع مع إبقاء الحساب غير مفعل وإحالته إلى مراجعة إدارية. لا يمحو التجديد قرار إيقاف أمني/إداري.
- تغيير الباقة أثناء التجديد يتطلب أن تكون الباقة والسعر والمدة محفوظة كلقطة ثابتة داخل Payment Intent؛ لا يعاد حساب السعر من إعداد متغير بعد الدفع.

### التوافق مع الكود الحالي

الوضع الحالي يحتوي `RegistrationRequest` مع `paid/processed/payment_ref` وتأكيد يدوي، وجدول `Client` مع `subscription_expires`. كما أن اعتماد التسجيل الحالي يحسب الانتهاء من الوقت الحالي مباشرة، ولا يطبق قاعدة التمديد من أكبر تاريخ بين الانتهاء الحالي والآن.

لذلك يجب أن تنقل المراحل التنفيذية منطق المال إلى Payment Intent وWallet Transaction وFulfillment مستقلين، ثم تبقي أعمدة التسجيل الحالية للتوافق أثناء ترحيل البيانات. لا يوضع منطق التجديد الجديد داخل endpoint قبول التسجيل القديم، ولا يعتبر رفع الإيصال دفعاً.

## 8. دور الذكاء الاصطناعي

يجوز استخدام نموذج لغوي في حالات محدودة:
- اقتراح حقول من نص إشعار جديد غير مطابق لقالب معروف.
- اقتراح اللغة أو إصدار قالب الإشعار.
- تلخيص سبب تحويل الحدث إلى المراجعة.

لا يسمح له:
- إنشاء أو تخمين رقم عملية أو مبلغ أو عملة غير موجودة.
- اعتبار إشعار مجهول المصدر دفعاً مسوّى.
- تجاوز عدم تطابق رقم المرسل أو المستقبل.
- اعتماد المبلغ أو التفعيل أو تعديل مدة الاشتراك.

كل نتيجة AI تبقى `untrusted extraction`، وتخضع للتحقق النوعي والقيود الحتمية؛ وإلا تتحول إلى مراجعة بشرية.

## 9. أمن الهاتف واستمرارية الخدمة

- هاتف Android مخصص، بقفل شاشة وتحديثات أمنية، دون Root، ولا يستخدم لتطبيقات شخصية أو حسابات محافظ أخرى غير المعتمدة.
- تثبيت APK موقّع من قناة إصدار موثوقة، وربط نسخة التطبيق والجهاز، مع إمكانية إلغاء الجهاز من الخادم.
- تخزين سر الجهاز محمياً بواسطة Android Keystore، مع تدويره وإلغائه عند الفقد أو إعادة الضبط.
- اتصال HTTPS فقط؛ يرفض الخادم التواقيع القديمة والطلبات المعادة.
- التطبيق لا يطلب صلاحية Accessibility أو SMS ولا يعرض أزراراً للتحكم بالمحفظة.
- عند انقطاع الهاتف أو سحب Notification Access، تظهر حالة `degraded` ولا يحدث تفعيل آلي حتى وصول حدث موثوق.
- إذا أخفت نسخة Android أو تطبيق المحفظة محتوى حساساً أو غيّرت التنسيق، لا يتجاوز SmartNet ذلك الحجب؛ ترسل الحالة للمراجعة.

## 10. خطة التنفيذ والاختبارات

### المرحلة 1 — قاعدة البيانات ومحرك الدفع
- جداول الأجهزة والمحافظ والهويات وPayment Intents والأحداث والمعاملات والمراجعات وFulfillment.
- قيود unique وAlembic migrations وفهارس البحث الآمن.
- قواعد المطابقة والتسوية وعمليات التفعيل/التمديد ذات idempotency.
- إبقاء وضع manual الحالي احتياطياً حتى اجتياز الاختبارات.

### المرحلة 2 — تطبيق Android
- اقتران الجهاز وNotification Listener وقائمة الحزم وطابور محلي مشفر.
- واجهة حالة الهاتف والأحداث المرسلة والأحداث التي تحتاج إعادة إرسال.
- عدم تضمين أي أسرار دفع في التطبيق.

### المرحلة 3 — Adapter لكل محفظة
- توفير أسماء الحزم الرسمية وعينات إشعارات حقيقية منزوعة البيانات الشخصية.
- اختبار كل قالب وحالات النجاح والانتظار والرفض والعكس والإلغاء وتعدد اللغات.
- تفعيل Adapter واحداً في كل مرة، مع زر إيقاف فوري.

### المرحلة 4 — لوحة الإدارة والتشغيل
- اعتماد هويات المرسلين لأول مرة، إدارة حسابات الاستقبال، قوائم المراجعة وسجل التدقيق.
- مراقبة heartbeat وفقد الإشعارات وفشل parsing وتراكم الطابور.
- تقارير يومية لمقارنة عدد وقيم الإشعارات والمعاملات الموثقة مع حركة المحفظة داخل التطبيق.

### اختبارات إلزامية قبل الإنتاج
- إشعار صحيح، مرسل غير معتمد، مرسل مطابق لعميل آخر، ومستقبل خاطئ.
- مبلغ/عملة مختلفان، عملية pending أو failed أو reversed.
- إشعار مكرر، مرجع مكرر، وإعادة إرسال من الهاتف بعد انقطاع.
- إشعاران بالقيمة نفسها، ووجود أكثر من Payment Intent محتمل.
- غياب رقم العملية، وتغير لغة أو تنسيق الإشعار.
- تجديد متزامن وحدث مكرر أثناء التفعيل.
- حساب موقوف إدارياً، طلب منتهي، دفع جزئي وزائد.
- فقد الهاتف، إلغاء الجهاز، سحب صلاحية الإشعارات، وتدوير سر الجهاز.
- تنفيذ كامل على MariaDB 11.8 مع اختبارات صلاحيات ونسخ احتياطي واستعادة.

## 11. شروط السماح بالتفعيل التلقائي

لن يفتح التفعيل التلقائي لمزود/محفظة حتى تتحقق الشروط التالية مجتمعة:
- اعتماد اسم الحزمة الرسمية وعينة إشعار صحيحة من نسخة التطبيق المستخدمة فعلياً.
- ثبوت أن صيغة الإشعار تعني دخول مبلغ نهائي إلى حساب الاستقبال، لا مجرد طلب أو إشعار أولي.
- قدرة Adapter على استخراج رقم العملية/مرجع فريد والمبلغ والعملة والمرسل والمستقبل.
- نجاح اختبارات التكرار والتعارض وإعادة الإرسال والعكس.
- اعتماد أول ربط لمحفظة صاحب الشبكة من مسؤول مخول.
- نجاح فترة تشغيل مراقبة (shadow mode): يسجل الوكيل قراراته المقترحة دون تفعيل، ثم تقارن النتائج مع سجل المحفظة.
- اعتماد مدير المنصة تشغيل الوضع الآلي لهذا المزود وحساب الاستقبال بشكل صريح.

إذا لم يعرض تطبيق المحفظة مرجعاً فريداً أو حالة تسوية موثوقة، يبقى الوكيل في وضع `candidate + manual review` لذلك المزود؛ ولا يتم اختراع ثقة لا توفرها القناة.

## 12. معلومات مطلوبة عند بدء التنفيذ الفعلي

قبل كتابة Adapters الخاصة بالمحافظ، يجب تحديد:
- أن الهاتف المخصص يعمل بنظام Android وإصدار النظام.
- أسماء تطبيقات المحافظ الفعلية المستخدمة وأسماء الحزم الرسمية لكل تطبيق.
- هل تعرض إشعاراتها رقم العملية والمرسل والمبلغ والعملة وحساب الاستقبال وحالة نهائية؟
- عينات إشعارات حقيقية بعد حذف أسماء الأشخاص وأرقامهم وأرقام الحسابات والمراجع والبيانات الحساسة، مع توضيح أي حقل تم حجبه.

لا ترسل كلمات مرور المحافظ أو PIN أو OTP أو صوراً تحتوي بيانات حساب حقيقية في مستودع Git أو المحادثة.

## مراجع Android

- [NotificationListenerService — Android API](https://developer.android.com/reference/android/service/notification/NotificationListenerService): استقبال الإشعارات المنشورة/المزالة، ومتطلبات تعريف الخدمة وانتظار `onListenerConnected()`.
- [NotificationManager — Android API](https://developer.android.com/reference/android/app/NotificationManager): التحقق مما إذا منح المستخدم التطبيق صلاحية Notification Listener.
- [Request special permissions — Android Developers](https://developer.android.com/training/permissions/requesting-special): الصلاحيات الخاصة تتطلب انتقال المستخدم إلى إعدادات النظام ومنحه الإذن.
